## 1. /newLobe never registered a LobeTable in standalone mode (hard bug)

### Symptom
Every `/lobeGrow` call returned:
```
!!! ERROR in /lobeGrow: Main.LobeTable.LobeTableError("No table found for
lobe 'X'. Call create_lobe_table! first.", "_get_chunk") !!!
```
even though `/newLobe` had just printed `Lobe 'X' created ...` milliseconds
earlier.

### Root cause
`Lobe.jl` starts with

```julia
if !isdefined(@__MODULE__, :LobeTable)
    include("LobeTable.jl")
    using .LobeTable
end
```

Julia's `@__MODULE__` here is `Lobe`, not the caller. At the time that
guard runs, `Lobe` has no `LobeTable` defined yet, so the `include`
always fires and creates a private `Lobe.LobeTable` submodule with its
own `LOBE_TABLE_REGISTRY`. Meanwhile `Main.jl` ran a second
`include("LobeTable.jl")` at top level, giving us a *sibling*
`Main.LobeTable` with a *different* registry. `Lobe.create_lobe!`
writes into the sibling inside itself; `/lobeGrow` later reads from
the top-level one. Two registries, neither complete, every grow
failed.

### Fix
Both loader sites now reuse the first copy they can find instead of
re-including:

- `src/Lobe.jl`: if the parent module (`Main` or the `GrugBot420`
  package) already has a `LobeTable`, reuse it via `getfield`. Fall
  back to `include` only when there is no parent copy.
- `src/Main.jl`: dropped the `include("LobeTable.jl")` at line 50
  entirely. We now pin `const LobeTable = Lobe.LobeTable` so the
  dispatcher and `Lobe` see the same registry. If `Lobe` did not
  bring one in, we `error(...)` loudly rather than quietly create
  a second copy (NO SILENT FAILURE).

After the fix `/lobeGrow` succeeds end-to-end --- verified by
planting 48 nodes across 6 lobes with zero errors.

## 2. `$VAR!` string interpolation landmines (9 latent crashers)

### Symptom
```
!!! SYSTEM ERROR: UndefVarError(:MAX_ATTACHMENTS!) !!!
```
A single `/nodeAttach` path that tried to trip the attachment cap
crashed not with the intended "max is 4" message but with an
`UndefVarError` because Julia parses `$name!` as the identifier
`name!` --- the `!` is a legal trailing character. The real error
message is never emitted. Every `error("... $var! ...")` in the tree
has this problem.

### Audit result
9 call sites had the pattern:

```
src/ChatterMode.jl:688        $last_input_time!
src/ImageSDF.jl:557           $base_idx!
src/ImageSDF.jl:694           $max_samples!
src/ImmuneSystem.jl:459       $node_count!
src/ImmuneSystem.jl:721       $aiml_node_count!
src/ImmuneSystem.jl:752       $aiml_node_count!
src/ImmuneThreadPool.jl:1496  $worker_id!
src/Main.jl:1887              $fmt!
src/Main.jl:4870              $MAX_ATTACHMENTS!
src/engine.jl:933             $elapsed_seconds!
```

### Fix
Wrapped every instance in explicit `$(var)` so the `!` stays in the
literal text. The intended human-readable error now actually fires.

## 3. MESSAGE_LOCK typo silently disabled pinned-memory citations

### Symptom
Every `/mission` emitted:
```
Warning: [MAIN v7.16 synthesis] Pinned-memory topicality check failed
(UndefVarError(:MESSAGE_LOCK)); skipping citation.
```
and pinned notes never appeared in Grug's output even though the
specimen had six relevant pins loaded.

### Root cause
`src/Main.jl:1650` locked `MESSAGE_LOCK`, which does not exist. The
actual global is `MESSAGE_HISTORY_LOCK` (declared at line 317). The
surrounding `try/catch ... @warn ...; skipping citation.` quietly
demoted the `UndefVarError` to a warning --- a textbook silent
failure disguised as error handling.

### Fix
Lock the real name, `MESSAGE_HISTORY_LOCK`. Added a block comment
explaining the trap so nobody reintroduces it. Pinned notes now
actually surface in the synthesis path --- verified by running the
driver again and seeing "Pinned note: every ai camp discovered one
biological mechanism and they all belong together" in a live
response scaffold.

## Known limitations (not fixed --- deliberate scope bound)

- `/saveSpecimen` does NOT bundle GroupRegistry state or the
  crystalize tag set. Groups/crystalize have their own
  `/groupSnapshot` + `/groupRestore` commands; reload from a main
  specimen leaves them empty. Arguably by design --- documented here
  so future readers don't chase it.

- `AIML_CONFIDENCE_THRESHOLD=0.15` fallback ("no vote cleared
  threshold") fires occasionally on short prompts. This is expected
  behaviour for a 48-node cave; it clears as the map grows toward
  the 1000-node latching threshold.
