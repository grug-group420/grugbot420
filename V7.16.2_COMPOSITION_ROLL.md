# v7.16.2 — Composition-Roll for Confirmed Support

## Problem

v7.16.1 introduced the relation-gated support band: a vote has to clear BOTH
a confidence floor AND a relation score before earning a "Grug also sure of:"
slot. That fixed the non-sequitur bug cleanly, but it left the rendering
format linear — every confirmed support claim was fenced off behind the
same template:

```
[primary claim]. Grug also sure of: [support claim]. Grug also sure of: [support claim 2].
```

User diagnosis:

> *"things it is sure of that get selected directly with top confidence votes.
> should just be part of the sentence not divided by GRUG ALSO THINK it
> should be part of the sentence structure."*

And with a follow-up:

> *"i dont think this should be linear. it should be about verbosity. see
> aiml is an orchestrator... how the orchestrator decides to string it
> together should by dynamic so maybe some coinflip actions here?"*

Confirmed support isn't a side note — it's corroborating evidence the
orchestrator has VERIFIED via the relation gate. It belongs woven into
the primary sentence, and the weaving should be DYNAMIC — the same facts
should produce different phrasings run to run, like actual spoken language.

## Fix (v7.16.2)

Confirmed-support rendering now runs through a **composition-roll** pipeline:

1. **Stitch registry** — a bank of rendering strategies, each with a
   strict gate (the condition under which it unlocks) and a weight
   (how often it wins the roll when multiple are available).
2. **Strict gating** — a stitch is eligible ONLY when its earning
   condition appears in `relation_score.reasons` (or is structurally
   true for `certainty == "UNSURE"` / pattern-length gates). No silent
   almost-matches.
3. **Weighted roll** — the eligible pool rolls weighted-random for
   the active stitch. Two fallback stitches are always in the pool
   so the roll can never come up empty.
4. **Render + telemetry** — the picked stitch's render function
   produces the prose fragment, and the orchestrator records which
   stitch fired per support node_id for debug visibility.

### Stitch registry (5 total this version)

| Stitch                 | Gate                                                          | Weight | Rendering example                                    |
|------------------------|---------------------------------------------------------------|-------:|------------------------------------------------------|
| `simple_connective`    | always (fallback)                                             |      1 | *"<p>, and <s>."*                                   |
| `rhetorical_hook`      | always (fallback)                                             |      1 | *"If <p>, then <s> too."*                           |
| `shared_subject`       | `"triples+"` appears in reasons                               |      4 | *"<p>; <s>."*                                       |
| `consequence`          | `"action-class+1"` in reasons                                 |      3 | *"<p>. That is why <s>."*                           |
| `concession`           | certainty == `"UNSURE"`                                       |      2 | *"<p>, though Grug also sees <s>."*                 |
| `elaboration`          | `length(s_pat) >= ceil(length(p_pat) * 1.3)`                  |      2 | *"<p>. More specifically, <s>."*                    |

The two fallbacks guarantee the pool is never empty; the four gated
stitches unlock based on what `relation_score` actually earned for this
(primary, support) pair.

### Data plumbing

- `SupportStitch` struct — `(name::Symbol, gate::Function, weight::Int, render::Function)`.
- `SUPPORT_STITCHES::Vector{SupportStitch}` — module-level constant, 6 entries.
- `_available_support_stitches(reasons, cert, p_pat, s_pat)` — walks the
  registry, evaluates every gate in `try/catch` with `@warn` on failure,
  and returns the subset that unlocked. Errors if the returned pool is
  ever empty (shouldn't happen — fallbacks are always in).
- `_roll_support_stitch(available)` — weighted-random pick using a
  normalized cumulative weight table. Short-circuits when pool size is 1.
- `_compose_support_stitch(primary_claim, primary_pattern, support_claim,
  support_pattern, reasons, certainty, support_node_id)` — the public
  entry point. Picks + renders; on render failure, logs `@warn` and
  falls back to `simple_connective` so the support claim never drops.
- `_CURRENT_SUPPORT_STITCHES` — per-cycle telemetry map
  `support_node_id → stitch_name`. Cleared at cycle start and in
  orchestrator `try/finally` so nothing leaks across cycles.

### Live demo output

Same primary claim, same support claim, different conditions:

**All gates unlocked** (reasons: `["triples+2 (sun,stars)", "action-class+1", "same-lobe+2"]`, UNSURE):

```
run 1: the sun is bright; stars emit light.                        <- shared_subject
run 2: the sun is bright, though Grug also sees stars emit light.  <- concession
run 3: the sun is bright, and stars emit light.                    <- simple_connective
run 4: If the sun is bright, then stars emit light too.            <- rhetorical_hook
run 5: the sun is bright. That is why stars emit light.            <- consequence
```

Five runs, five distinct phrasings. Full demo in `test_run/v7162_stitch_demo.md`.

### Debug telemetry addition

The `--- DEBUG TELEMETRY ---` block now includes a stitch-breakdown
sub-block when any confirmed support was rendered:

```
Support Actions (relation-linked, composed INLINE with primary): [describe, explain]
Support Stitches (v7.16.2 composition-roll):
  - node_11 -> shared_subject
  - node_17 -> consequence
```

Every confirmed support claim shows exactly which stitch carried it.

## Error handling

- Every stitch gate is wrapped in `try/catch`; a broken gate logs
  `@warn` and is skipped (that stitch just doesn't unlock this cycle).
- An empty available pool is impossible (fallbacks are always in) but
  it's asserted anyway with a FATAL error if ever reached.
- Render failures log `@warn` and fall back to `_stitch_render_simple_connective`
  so the confirmed support claim never gets dropped.
- Telemetry dict is cleared at orchestrator start AND in `try/finally`
  so mid-cycle crashes can't leak stitch names to the next cycle.
