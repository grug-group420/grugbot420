# v7.16.1 — Relation-Gated Support Band + Reliability-Flagged Hedge

## Problem

v7.16.0 introduced the three-band orchestrator (top / support / hedge), and it
shut down the v7.15 babble bug. But it revealed a new issue: **support-band
inclusion was purely a confidence check**. Any vote landing in
`[AIML_SUPPORT_FLOOR, top_max)` got promoted to "Grug also sure of: …",
regardless of whether its pattern had anything to do with the primary claim.

The seeded conversation showed this on Turn 23 ("what is joy and when does it
come"). The primary vote was `describe` for node_11 on the joy frame, but a
nature-lobe vote for `bees pollinate flowers and forge honey` hit the support
floor at confidence 0.38 and was rendered as:

> *"A companion frame: bees pollinate flowers and forge honey."*

attached to the joy answer. Loud but off-topic.

User diagnosis:

> *"the other votes it selects that are hard lock ins and not coinflips?
> should be any secondary vote with direct semantic or pattern relations with
> the primary votes. is this a good idea?"*

Yes — and with a follow-up:

> *"it should go by both confidence and relationals. also where it has GRUG
> ALSO SAY for left overs? should make sure the user knows these details
> might be less reliable off the bat"*

## Fix (v7.16.1)

Support-band inclusion now requires **BOTH**:

1. Confidence ≥ `AIML_SUPPORT_FLOOR` (0.35), AND
2. Relation score ≥ `AIML_SUPPORT_RELATION_FLOOR` (2)

Anything that meets (1) but fails (2) is demoted to a new **unlinked-support**
band with an explicit reliability warning in the speech output. Hedge band
renders with its own explicit caveat. No silent demotions.

### relation_score(primary, primary_node, candidate, candidate_node)

Six independent axes, each wrapped in try/catch with `@warn` on failure (no
silent fall-through):

| Axis                         | Points | Source                                                   |
|------------------------------|-------:|----------------------------------------------------------|
| Group-registry partners      |     +3 | `GroupRegistry.partners_for_node`                        |
| Attachment pair (either dir) |     +3 | `ATTACHMENT_MAP`                                         |
| Same lobe                    |     +2 | `Lobe.find_lobe_for_node`                                |
| Connected lobe               |     +1 | `Lobe.LOBE_REGISTRY.connected_lobe_ids`                  |
| Shared triple tokens (cap 2) | +1 ea. | `Vote.node_triples`, length ≥ 3 tokens                   |
| Action concept-class overlap |     +1 | `Thesaurus.concept_classes_of(action)`                   |
| Pattern concept-class (cap 1)|     +1 | `Thesaurus.concept_classes_of(pattern tokens)`           |

Max achievable per candidate: `3 + 3 + 2 + 2 + 1 + 1 = 12` (or 3+3+1+2+1+1=11
if lobes are connected rather than same). Floor of 2 clears with either
same-lobe alone, OR triple overlap ≥ 2, OR attachment/group alone (+3), OR
any two independent axes at +1 each.

Self-match is short-circuited to `score=0, reasons=["self-match-ignored"]`.

### Four-way band assignment

`ephemeral_aiml_orchestrator` now does:

```
(top_tier, support_tier, hedge_tier, rejected) = select_aiml_votes_banded(votes)

# primary pick from top tier (tie-breaker)
primary = pick_primary(top_tier)

# Split support_tier by relation gate
confirmed_support = [v for v in support_tier if relation_score(primary, v) >= 2]
unlinked_support  = [v for v in support_tier if relation_score(primary, v) <  2]

_CURRENT_BAND_INFO maps node_id -> :top | :support | :support_unlinked | :hedge
_CURRENT_RELATION_SCORES maps node_id -> (score, reasons) for telemetry
```

Side-channels cleared in `try/finally`, so any crash between orchestration
and dispatch can't leak state to the next cycle.

### generate_aiml_payload — user-visible reliability warnings

The payload now emits four distinct rendering frames:

| Band                | Rendering                                                              |
|---------------------|------------------------------------------------------------------------|
| `:top`              | Primary claim + any tied alternatives as hedge companions              |
| `:support`          | `" Grug also sure of: <pattern>."` (cap 2, deduped vs. primary)        |
| `:support_unlinked` | `" Grug heard this strongly too but is not sure it fits here (take with caution): <pattern>."` (cap 2) |
| `:hedge`            | `" Less certain — Grug also picked up <actions> but these may not hold up."` (UNSURE only, deduped) |

The three reliability-flagged frames are the direct response to the user's
"should make sure the user knows these details might be less reliable" ask.
User gets unambiguous signal that the trailing content is lower-trust.

### Debug telemetry

`--- DEBUG TELEMETRY ---` block now shows:

```
Support Actions (relation-linked, render as 'Grug also sure of'): [...]
Unlinked Support (loud but off-topic, reliability-flagged): [...]
Hedge Actions (quiet voices, reliability-flagged): [...]
Relation Scores (floor=2):
  - SUPPORT   node_11:describe score=4 [same-lobe+2, action-class+1, pattern-class+1]
  - UNLINKED  node_7:analyze    score=1 [connected-lobe+1]
  - HEDGE     node_3:explain    score=0
```

Per-candidate breakdown makes it trivial to see *why* each support decision
was made. No more mystery at the tie-break boundary.

## Tests

New: `test/test_support_relation_gate.jl` — 22 assertions across 10 testsets:

- Floor constant is pinned at 2
- Self-match returns score=0 with `"self-match-ignored"` reason
- Unrelated nodes score 0 (baseline)
- Shared triple tokens earn +1 each, capped at +2
- Short (<3 char) tokens filtered out of triple overlap
- Action concept-class overlap earns +1 via seeded "inquiry" class
- Pattern concept-class overlap earns +1 via pattern tokens
- Multi-axis scoring crosses the floor cleanly
- Group-registry partners earn +3
- Single-member groups DON'T earn +3 (baseline stays cold)

Full suite: **38/38 tests passing** (up from 37 in v7.16.0).

## Error handling

Every `relation_score` axis is wrapped in `try/catch` with `@warn` logging
the failure (`GroupRegistry lookup failed`, `Attachment map lookup failed`,
`Lobe lookup failed`, `Triple token check failed`, `Action concept-class
check failed`, `Pattern concept-class check failed`). A failure on one axis
doesn't zero the rest — the function just skips that point source and
returns whatever the other axes earned. No silent swallows.

Side-channel dicts (`_CURRENT_BAND_INFO`, `_CURRENT_RELATION_SCORES`) are
cleared in `try/finally`, so a mid-orchestration crash can't pollute the
next cycle's band lookups.
