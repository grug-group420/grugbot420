# v7.16.3 — Absolute Lock-In Floor with Semantic Weighting

## GRUG Intent (user's words)

> "any vote of a certain confidence threshold should be a lock in. it shouldnt
> limit top votes. top votes are just based on confidence threshold. this way
> for complex questions it still works"

> "yeah have top confidence semantic and confidence weigh ins. use both."

The previous top-tier was defined as a **relative** window around the highest
vote (`AIML_TOP_TIER_WINDOW = 0.05`). That meant a complex question with three
genuinely strong peers would still only promote votes within 0.05 of the
single highest one. v7.16.3 replaces that gate with an **absolute combined
score floor** so every vote that clears the bar locks in, however many of
them there are.

## The Rule

For every vote `v` with the peer field = all votes with
`confidence >= AIML_SUPPORT_FLOOR (0.35)`:

```
linkage_raw       = max( relation_score(v, p).total for p in peers, p != v )
linkage_norm      = clamp(linkage_raw / AIML_RELATION_SCORE_MAX, 0.0, 1.0)
combined_score(v) = confidence(v) + AIML_SEMANTIC_WEIGHT * linkage_norm
locked(v)         = combined_score(v) >= AIML_TOP_LOCKIN_FLOOR
```

Constants (pinned in `VoteOrchestrator.jl`):

| Constant                     | Value | Meaning                                   |
|------------------------------|-------|-------------------------------------------|
| `AIML_TOP_LOCKIN_FLOOR`      | 0.50  | Absolute combined-score bar               |
| `AIML_SEMANTIC_WEIGHT`       | 0.15  | How much linkage can move the needle      |
| `AIML_RELATION_SCORE_MAX`    | 12    | Divisor for normalizing raw relation score|
| `AIML_SUPPORT_FLOOR`         | 0.35  | Unchanged; defines the peer field         |
| `AIML_TOP_TIER_WINDOW`       | 0.05  | **Demoted** to tie-break-only role        |

`AIML_TOP_TIER_WINDOW` is kept (commented as tie-break-only) so downstream
code that already uses it for ordering keeps working without surprises. The
promotion pass runs BEFORE that window is consulted, so the window only ever
sees the post-floor top tier.

## The Promotion Pass — Unified & Symmetric

`_apply_lockin_promotion(top_votes, support_votes, hedge_votes)` evaluates
EVERY top and support vote with the same rule:

1. Build the peer field from top ∪ support where `confidence >= 0.35`.
2. For each candidate, compute `linkage_raw`, `linkage_norm`, `combined`.
3. `locked = combined >= 0.50` → goes to `promoted_top`.
4. `locked = false` → goes to `demoted_support` (regardless of where it
   started).
5. If `promoted_top` is empty after the pass, pick the single
   highest-combined candidate, push it to `promoted_top` with
   `locked = false`, and set `emergency_fallback = true`. The orchestrator
   emits a `@warn` when this fires.

Hedge votes are never evaluated or promoted — they stay hedge. This matches
the existing anti-ignite rule: a sub-0.35 vote cannot drive a response no
matter how much linkage it has.

## Why the Symmetric Rule Matters (the bug it killed)

First draft of v7.16.3 only re-scored the *support* list and unconditionally
marked every original *top* vote with `locked = true`. That broke the
invariant: seeded-conversation replay showed `LOCKIN node_48 conf=0.395
combined=0.412` — a vote below the floor tagged as locked because it was
already in `top_votes` before the pass. Telemetry was lying.

Fix: one evaluator, both lists. A vote earns `locked` by clearing the floor
on this pass — never by its starting bucket. The test "emergency fallback
fires when nothing clears the floor" guards the regression.

## Emergency Fallback

For questions where the cave simply doesn't know enough yet, the whole pool
may sit under 0.50 combined. Rather than silently return nothing, the pass:

- Promotes the argmax-by-combined vote to top.
- Leaves `locked = false` in its telemetry entry (honest — it did NOT clear
  the floor).
- Sets `emergency_fallback = true` on the returned NamedTuple.
- The orchestrator logs `@warn "[ORCHESTRATOR v7.16.3] No vote cleared
  AIML_TOP_LOCKIN_FLOOR=0.5. Emergency fallback: promoted highest-combined
  vote '<node>' to keep cave talking."`

No silent failures. Cave keeps talking. Operator sees exactly when the
confidence floor was missed.

## Telemetry

`_CURRENT_LOCKIN_SCORES::Dict{String, NamedTuple}` records every vote
touched by the pass with fields:

- `confidence`
- `linkage_raw`
- `linkage_norm`
- `combined`
- `locked::Bool`

Debug block in `generate_aiml_payload`:

```
Lock-In Scores (floor=0.5, w_sem=0.15):
  - LOCKIN node_34 conf=0.648 link=0.0 combined=0.648
  -        node_44 conf=0.389 link=0.417 combined=0.452
  -        node_14 conf=0.389 link=0.417 combined=0.452
  ...
```

Sorted by combined score descending. `LOCKIN` prefix only when `locked ==
true`. Cleared in the orchestrator's `try/finally` alongside the other
v7.16.x side-channels (`_CURRENT_BAND_INFO`, `_CURRENT_RELATION_SCORES`,
`_CURRENT_SUPPORT_STITCHES`).

## Composition with v7.16.2

v7.16.2's composition-roll stitch registry is untouched. The only coupling:
after v7.16.3 promotes a support vote to top, that vote is no longer a
"support claim" and no stitch fires for it. Support stitches only compose
the votes that v7.16.3 decided to keep in the support band — by design.

## What Did NOT Change

- `AIML_SUPPORT_FLOOR = 0.35` — still the gate for the peer field and for
  the support band itself.
- Hedge band rules — still defined by confidence alone, never relation.
- Stitch gating in `SUPPORT_STITCHES` — still strictly scored off
  `relation_score(...).reasons`.
- Tie-break ordering within the top tier — still uses the 0.05 window for
  stable sorting once the floor is cleared.
