# v7.15 Whitepaper Addendum --- Sequential Lobe Orchestration & Vote-Swap Chatter

Versions 7.9 through 7.14 built out the per-activation entropy framework, the
two-stage fresh-memory gate, and the digest-only message history. Those were
all refinements to the inside of the orchestration pipeline. v7.15 changes how
the pipeline itself is scheduled.

## 15.16 Sequential Lobe Orchestration v7.15

The old BrainStem picked one winning lobe and muted every other lobe for the
turn. That was too sharp. A second lobe with a real contribution silently
disappeared, and cross-talk paths that wanted to surface related nodes from
the muted lobes had nowhere to land. The v7.15 orchestrator (implemented in
`src/LobeOrchestrator.jl`) replaces that winner-take-all with a two-tier
scheme: one lobe always gets the floor first, and other lobes that clear a
two-factor quality gate get an async turn right after, ordered by strength.

**Curved-average floor selection.** Each lobe's vote pool collapses to a
single ranking number via

    base_avg   = mean(all vote confidences cast by the lobe this cycle)
    top_avg    = mean(votes within TOP_WINDOW = 0.05 of the lobe's max conf)
    curved_avg = base_avg * top_avg

The multiplication is the curve. A lobe with many mediocre votes cannot
outrank a lobe with a smaller set of high-confidence votes: the curve drags
base_avg down proportionally whenever top_avg is weak. The lobe with the
highest curved_avg wins the floor. Exact ties resolve by a fair 50/50 (really
1/N) coinflip; the diagnostic flag `tie_resolved_by_coinflip` rides along so
the logger can surface ties when they happen.

**Multi-lobe async gate.** A lobe may join the floor winner in async execution
only if BOTH of these hold:

    curved_avg >= MULTI_LOBE_THRESHOLD      (default 0.35)
    winning_vote_count >= MIN_WINNING_VOTES (default 2, vote >= 0.55)

The two-factor gate prevents the common failure mode where a lobe accumulates
many small votes (passing the threshold by addition without any clear winner)
or scores one freak high vote (passing the winning count with a single
outlier). Only lobes with real vote mass AND real vote quality earn async
access. When the floor winner itself fails the gate (everyone is weak),
secondaries are refused: a weak floor does not imply a strong neighborhood.

**Hard caps.** Each lobe that speaks, floor or async, is bounded by
`PER_LOBE_FIRE_CAP = 1000`. Cross-talk activations (attach relays, drop-table
cascades, semantic-bridge fires across multiple speaking lobes) share a
single `CrossTalkGate` whose cap is `CROSS_TALK_ACTIVE_CAP = 1000` regardless
of how many lobes are involved. The gate uses a lock-guarded atomic counter;
`try_claim_cross_talk!` returns false when the cap is hit and the caller
skips that cross-talk firing, surfacing an observable backpressure signal
instead of silently blowing through.

## 15.17 GroupRegistry & Vote-Swap Chatter v7.15

Chatter was rebuilt for v7.15. Two principles drove the rewrite:

1. **Patterns are identity.** The v7.1 chatter copied *pattern* tokens from
   strong nodes to weak ones. That eroded the receiver's original lexical
   shape over time. v7.15 copies *votes* --- the winning action and its
   weight --- instead. Strong nodes still signal, weak nodes still learn,
   but they learn "what action would you have taken here?" not "what words
   would you have used?" Identity survives; behavior propagates.

2. **Groups, not ad-hoc pools.** Every node that participates in chatter is
   a member of one or more groups registered in `src/GroupRegistry.jl`. Each
   node is assigned a random partner cap in `[PARTNER_CAP_MIN, PARTNER_CAP_MAX]
   = [8, 16]` at first group-join; hitting the cap flips the group's
   `is_unlinkable` flag. Graves inside a group temporarily suppress
   `is_unlinkable` so replacements can join without waiting for a global
   capacity rebuild --- graves are memory, not bloat, same principle as the
   AIML tribes in section 8.5.

**Chatter windowing.** During idle time, the chatter scheduler asks the
registry for `next_chatter_window_ids(; window_size)` where `window_size` is
a random draw in `[CHATTER_WINDOW_MIN, CHATTER_WINDOW_MAX] = [100, 400]`. The
registry walks the group id list in insertion order (FIFO), wrapping at the
end, and advances a persistent cursor so the next window begins where the
last one ended. The full registry --- groups, cursor, unlinkable flags ---
snapshots to a gzipped JSON file on disk via `save_registry_compressed`,
giving crash recovery and between-run continuity.

**Vote-swap rules (`src/ChatterVoteSwap.jl`).** For each group in the chatter
window:

- **Cooldown:** each node may receive at most one vote per
  `CHATTER_COOLDOWN_SECONDS = 3600` (one hour). Cooldown is per-node, tracked
  in `_COOLDOWN_MAP`, and enforced by `can_chatter_now`. A never-chattered
  node passes the gate by exception; a freshly-chattered node fails it for
  the next hour regardless of how many chatter windows fire in between.
- **Weak-only receiver:** sender must be strictly stronger than receiver.
  Strong nodes never receive copies --- this is the anti-identity-loss rule.
- **Semantic gate:** the swap fires only if `should_swap_vote(intensity)`
  returns true. Intensity is computed per-pair by the engine's semantic
  layer (relational-triple overlap, shared required-relations, thesaurus
  proximity) and clamped to `[0, SEMANTIC_INTENSITY_CAP = 1.0]`. The gate
  is a coinflip with `p = 0.10 + (intensity / cap) * 0.85`, saturating at
  0.95 so exploration is never silenced fully.
- **At most one swap per node per round:** the round runner tracks a
  `swapped_this_round` set so a weak node in two groups this window still
  accepts at most one copy. This is independent of the 1-hour cooldown ---
  the per-round limit is a round-local rule; the cooldown is time-local.
- **Weight jitter:** the donated vote's weight is passed through
  `jitter_vote_weight(w; ratio = WEIGHT_JITTER_RATIO = 0.03)`, zero-mean
  uniform within `[-ratio*|w|, +ratio*|w|]`. If the donated vote has no
  weight (effectively zero), `maybe_attach_default_weight` flips a
  `DONATED_BARE_WEIGHT_PROB = 0.5` coin; on heads, the weight becomes
  `DONATED_BARE_WEIGHT = 0.25`. Chatter thus never multiplies a zero-weight
  donation into a zero-weight receipt without a chance to materialise.

## 15.18 CRYSTALIZE Tag v7.15

The CRYSTALIZE tag (defined in `src/CrystalizeTag.jl`) marks a node as
always-fire at the attachment relay layer. A crystalized attached node skips
the strength-biased coinflip and always fires when its target fires. Two
origins feed the same fire-path:

- **User-issued:** `mark_user_crystalized!(node_id)` promotes a node by
  operator command. Useful for anchoring high-importance policy nodes that
  must never miss a turn.
- **Auto-crystalizer:** during idle time, the maintenance loop checks each
  strong node against `should_auto_crystalize(strength, avg_semantic_truth)`.
  Promotion requires `strength >= AUTO_STRENGTH_FLOOR = 7.5` AND
  `avg_semantic_truth >= AUTO_SEMANTIC_FLOOR = 0.70`. Hysteresis keeps the
  node crystalized while `strength >= AUTO_STRENGTH_RELEASE_FLOOR = 6.0`;
  dropping below that floor revokes the auto tag on the next maintenance
  sweep.

User and auto tags live in separate sets. `uncrystalize!(id; user=true,
auto=true)` defaults to clearing both, but `uncrystalize!(id; user=false,
auto=true)` is the revocation call the auto-maintainer uses, guaranteeing
it can never yank a user-issued tag.

## 15.19 Dynamic Action/Tone Prediction v7.15

`src/DynamicActionTonePredictor.jl` is a thin wrapper around the classic
`ActionTonePredictor.predict_action_tone`. The wrapper first computes the
cheap complexity score used by `screen_input_complexity`:

    complexity = (signal_length * 0.15) + (triple_count * 1.5)

If `complexity < COMPLEXITY_FLOOR = 4.5`, the wrapper returns the base
prediction bit-exact --- zero overhead, zero behavior change. Only inputs at
or above the floor enter the dynamic re-weighting path, where the base
confidence is boosted by `min(CONFIDENCE_BOOST_CAP = 0.30, signals *
PER_SIGNAL_BOOST = 0.05)` with `signals = triple_count + causal_verb_count`.
Rich inputs therefore produce more confident predictions; simple inputs
produce the classic output. Action and tone families, arousal nudge, weight
multiplier, and incomplete-chain flag all pass through unchanged --- only
confidence is moved by the dynamic path.

## 15.20 Strong-Node-Low-Confidence Jitter Override v7.15

The NONJITTER tag (section 15 v7.20) lets a node silence the post-fusion
micro-jitter on its end-confidence. That is correct for most "stable" strong
nodes, but wrong for one specific corner: a strong node that cast a *low*
confidence this cycle. Without jitter, that node stays deterministically low
and cannot naturally reclaim the floor --- the tag locks it out of its own
recovery path.

`src/RelationalJitter.jl` now exposes `strong_low_conf_override(strength,
confidence)` and `jitter_score_with_override(score; strength, nonjitter,
confidence)`. The rule is:

    nonjitter == false                              -> always jitter
    nonjitter == true AND strong_low_conf_override  -> jitter anyway
    otherwise                                       -> identity (honor tag)

`strong_low_conf_override` is true when `strength >=
NONJITTER_OVERRIDE_STRENGTH_FLOOR = 7.5` AND `confidence <
NONJITTER_OVERRIDE_CONF_CEIL = 0.35`. Callers use the single helper so the
rule lives in exactly one place and can't drift between call sites.

## 15.21 PhagyGroupOrganizer Automaton v7.15

A new idle-time automaton in `src/PhagyGroupOrganizer.jl` runs alongside the
six automata in section 11. Three jobs per pass:

1. Clear any stale `is_unlinkable` flag on a group that has `grave_count >
   0` (graves opened a slot; the flag should have cleared but didn't).
2. Prune groups whose `member_ids` is empty and `grave_count == 0` (truly
   empty --- no live, no memorial).
3. Compact the chatter cursor if it has run off the end of the group id
   list after step 2.

An optional `auto_snapshot=true` kwarg saves a compressed JSON snapshot of
the registry after the organize pass. The organizer never runs two passes
in parallel (the registry's internal lock serializes mutating calls), and
it returns a typed `GroupOrganizerStats` so the phagy logger can include
the organizer's counts in its cycle summary.

---

All seven additions follow the project-wide no-silent-failures policy: every
error path throws a typed exception with a named context breadcrumb, every
rejection in a round runner is counted (not swallowed), and every public
mutator that could receive bad input validates before state mutation. Test
coverage: 7 new files, 170+ assertions, full-suite green (32/32).
